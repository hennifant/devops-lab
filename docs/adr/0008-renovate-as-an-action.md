# 0008. Renovate as a self-hosted Action, and a pinned base image digest

Date: 2026-08-17
Status: Accepted

## Context

Two related gaps.

`FROM python:3.14-slim` is a moving tag. The same commit builds on a different base
image next month. Pinning the digest fixes that but creates a worse problem on its own:
a hand-pinned digest never receives security patches, because nobody remembers to bump
it. Pinning is only defensible if something keeps it current.

Separately, all Python dependencies became pinned in
[0006](0006-compiled-requirements-with-uv.md), which turns every upgrade into manual work,
and the workflow actions in `.github/workflows/` were several major versions behind
without anyone noticing.

Both problems have the same shape: pinning without automation is how a repository
quietly rots.

## Decision

Pin the base image to its multi-architecture index digest:

```dockerfile
FROM python:3.14-slim@sha256:ce40764625a4ff50df3548277632e7f96c4e77fe75fa848aae9885476e7df5a4
```

Run **Renovate as a scheduled GitHub Action in this repository**, not as the hosted
Renovate GitHub App. Configuration in `renovate.json`; `pinDigests` scoped to the
`dockerfile` manager; updates grouped so a run produces two pull requests rather than a
dozen.

Requires a `RENOVATE_TOKEN` repository secret.

## Consequences

- Reproducibility and patching stop being in tension: the digest is fixed per commit, and
  Renovate opens a pull request when the tag moves.
- No third party is granted access to the repository. Every Renovate run is visible in
  this repository's own Actions logs, which also makes it debuggable.
- The credentials live here. `RENOVATE_TOKEN` is a repository secret, so anyone who can
  push to `main` can exfiltrate it. The hosted App would not have that property. This is
  the deliberate trade.
- Renovate runs are billed against this account's Actions minutes; the App is free.
- A dependency dashboard issue appears and needs occasional attention, or it becomes
  noise that gets ignored — which is the usual failure mode of automated update tooling.
- The first run will propose upgrading every workflow action at once. That is intended:
  the existing versions were left stale specifically so the first run demonstrates what
  Renovate does and produces a reviewable diff.

## Background

**Why Renovate rather than Dependabot.** Dependabot is built into GitHub and needs only a
config file, which is genuinely simpler. It can *update* a Docker digest but cannot
*introduce* one. Renovate's `pinDigests` rewrites `FROM python:3.14-slim` into the
digest-pinned form itself and then maintains it. Since digest pinning was the goal, that
capability decided it.

**Why the Action rather than the App.** The hosted App is the normal choice and requires
no token management. It is also an external service with write access to the repository.
Given that this repository's other credentials were deliberately scoped down to a single
repository, granting a third party broader access would be inconsistent. Running Renovate
as an Action keeps the trust boundary where the rest of the setup already put it, and
seeing the tool's own logs is worth something in a learning lab.

**The index digest, not a platform digest.** The image builds for `linux/amd64` and
`linux/arm64`. `python:3.14-slim` resolves to an OCI image *index* that lists one
manifest per architecture. Pinning the index digest keeps multi-architecture builds
working; pinning a per-platform manifest digest would break one of the two. Resolved with:

```bash
tok=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/python:pull" | jq -r .token)
curl -sI -H "Authorization: Bearer $tok" \
  -H "Accept: application/vnd.oci.image.index.v1+json" \
  https://registry-1.docker.io/v2/library/python/manifests/3.14-slim | grep -i docker-content-digest
```

**The `pip-compile` manager needs enabling.** Renovate ships it with an empty
`managerFilePatterns`, so it matches nothing until configured. It reads the header that
`uv pip compile` writes:

```
# This file was autogenerated by uv via the following command:
#    uv pip compile --universal requirements.in -o requirements.txt
```

and replays that command to regenerate the lock, which is why the header must not be
suppressed with `--no-header`. The `.in` files are handled by the separate
`pip_requirements` manager; both are pointed at explicit patterns here so they cannot
both claim the same file.

**`schedule` is not "when Renovate runs".** It restricts when Renovate may *create
branches*, independently of when the process starts. Self-hosted, the cron in
`.github/workflows/renovate.yml` already decides when it runs, so a `schedule` in
`renovate.json` is a second gate that silently blocks manual `workflow_dispatch` runs:

```
Skipping branch creation as not within schedule (branch=renovate/major-github-actions)
```

The configuration therefore sets no schedule at all. The same trap applies to
`lockFileMaintenance.schedule` — a monthly window would almost never coincide with a
weekly cron, and the maintenance would simply never happen.

**Token permissions.** The fine-grained PAT for `RENOVATE_TOKEN` needs Contents and Pull
requests (write, to push branches and open pull requests), Issues (write, for the
dependency dashboard), and Workflows (write, or it cannot modify anything under
`.github/workflows/`). Metadata read is mandatory.

**Not done: pinning actions to commit SHAs.** `pinDigests` applied to the
`github-actions` manager would rewrite `actions/checkout@v4` to a commit SHA, which
defends against a tag being re-pointed at malicious code. It is a real hardening step and
deliberately deferred — it belongs with the Phase 4 supply chain work.

## Known limitations

*Observed on the first run, 2026-08-17.*

Docker Hub refuses anonymous tag enumeration beyond roughly page 10:

```
GET https://hub.docker.com/v2/repositories/library/python/tags?…&page=11  → 403
hostRules: no authentication for hub.docker.com
```

Renovate can therefore miss newly published *tags* for `python` and `postgres` — a future
`3.15` might go unnoticed. Digest lookups for an already-pinned tag go through
`index.docker.io` and appear unaffected, but that has not yet been confirmed by a run in
which the digest actually moved.

### Transitive pins must not be bumped individually

*Observed 2026-08-19, after it broke `main`.*

Renovate proposed `pydantic-core` 2.46.4 → 2.48.0. `pydantic==2.13.4` pins
`pydantic-core==2.46.4` exactly, so the resulting lock was unsatisfiable and every install
failed:

```
Because pydantic==2.13.4 depends on pydantic-core==2.46.4 and you require
pydantic-core==2.48.0, we can conclude that your requirements are unsatisfiable.
```

The `pip-compile` manager had classified it correctly — `depType: indirect`, `is disabled`.
The update came from `pip_requirements`, which had also claimed the `.txt` files, because
**`managerFilePatterns` adds to a manager's built-in patterns rather than replacing them.**
`pip_requirements` matches `requirements.txt` by default; pointing it at `.in` files added
a pattern without removing that one. To that manager a compiled lock is just a list of
pins, with no notion of `# via pydantic`.

Two package rules now close it: `pip_requirements` is disabled for the `.txt` files, and
`pip-compile` is disabled for `indirect` deps. Transitive versions change only through
`lockFileMaintenance`, which re-resolves the whole graph.

The wider lesson is not about Renovate. CI ran on that pull request and failed, and the
merge went through anyway because `main` has no required status checks. The bot proposing
an impossible update is normal; nothing stopping it from landing is the actual defect.

The fix would be a Docker Hub account plus a token, supplied through `hostRules`. That is
another credential to manage for a narrow benefit, so it is deliberately not done. Revisit
if a base image upgrade is ever missed.
